# Управляемое закрытие GUI (F8)

Канал `velum/window` обслуживает оба направления:

- GTK `delete-event` и Windows `WM_CLOSE` всегда блокируют обычное уничтожение
  окна и посылают Dart событие `closeRequested`.
- Flutter X вызывает `VelumTrayService.handleWindowClose()`. Пункт «Выход»
  вызывает `exitApplication()`, который игнорирует настройку сворачивания.
- Только команда Dart `closeConfirmed`, отправленная после очистки либо после
  явного согласия пользователя на небезопасный выход, разрешает окончательное
  закрытие. Нативный флаг разрешения предотвращает рекурсивный запрос.
- Если Dart ещё не готов, отсутствие обработчика не разрешает закрыть окно.

Контроллер выполняет один запрос закрытия за раз. Повторные X, Alt+F4 и «Выход»
присоединяются к этому Future. Начатые обновления трея дожидаются завершения,
а его уничтожение выполняется один раз. Прямого `exit(0)` больше нет.

## Скрытие

При включённом minimizeToTray скрытие допускается после создания иконки и
проверки её доступности непосредственно перед действием. Linux дополнительно
проверяет зарегистрированный SNI host и наличие элемента текущего процесса в
`RegisteredStatusNotifierItems`; одной доступности session D-Bus недостаточно.
Если `gdbus` отсутствует, запрос не подтверждён либо формат регистрации не
распознан, окно не скрывается. Windows использует фактическую видимость иконки
из nativeapi, которая проверяет её наличие в Shell.

### Восстановление скрытого окна на Linux (F9)

После нативного `hide()` выполняется повторная проверка. Если host исчез в
промежутке между первой проверкой и скрытием, окно сразу показывается обратно;
это не запускает процедуру выхода, disconnect или восстановление System Proxy.
Пока окно скрыто через Velum, работает одноразовый таймер: следующая проверка
назначается через одну секунду после завершения предыдущей. Проверяются и SNI
host, и регистрация элемента текущего процесса. Потеря любого из них или ошибка
проверки вызывает показ окна. Ошибка нативного show оставляет наблюдение активным
для следующей попытки. После успешного показа фоновый опрос прекращается.

Это ограниченный опрос, не подписка на D-Bus: отдельного постоянного дочернего
процесса/новой зависимости нет. Видимое окно и статистика VPN не запускают эти
проверки. Для фонового наблюдения нет параллельных запросов и накопления ticks:
при медленной проверке новый таймер назначается только после её завершения.
Пользовательский запрос скрытия отдельно выполняет preflight. Каждый gdbus call
сохраняет тайм-аут ответа в одну секунду; проверка может последовательно обратиться
к двум watcher и двум свойствам. Поэтому восстановление не имеет гарантированного
субсекундного срока: влияют тайм-ауты, загрузка GLib/Dart и планировщик ОС.

У cnativeapi 0.5.10 SNI-регистрация выполняется при создании иконки; автоматической
подписки на перезапуск watcher нет. Если preflight не подтвердил доступность,
следующий запрос пользователя один раз пересоздаёт иконку и её меню, затем снова
проверяет регистрацию. Это возвращает возможность скрытия после появления панели
без перезапуска Velum. При отсутствии панели окно остаётся доступным; для X
сохраняется описанный выше управляемый сценарий выхода. Повторная регистрация
сериализована с обновлением/уничтожением трея. Windows сохраняет прежнюю проверку
видимости Shell-значка и не использует Linux-опрос/пересоздание при preflight.

Нативные hide/show/close проходят через очередь. Более новый show отменяет ещё
не выполненный hide; если hide уже начат, show следует после него. Состояние
скрытия меняется внутри этой очереди, чтобы новый hide во время старого show
не остался без наблюдения. Повторные hide объединяются. Ответ фонового запроса
проверяется по версии оконного запроса и не влияет на новую сессию скрытия.

Показ окна и выход отменяют таймер. Dispose также отменяет наблюдение, снимает
слушателей и ставит best-effort show после уже принятой нативной операции, если
Velum скрывал окно. Уже запущенный ограниченный gdbus probe может завершиться,
но его результат после dispose не меняет окно и не создаёт новых таймеров.
Повторный initialize того же объекта не создаёт слушателей/таймеров; уничтоженный
объект не запускается заново. Новый экземпляр начинает собственный жизненный цикл.

## Завершение и ошибки

При возможном активном соединении GUI сначала предупреждает об изменении
защиты/пути трафика. После согласия `prepareForExit()` использует существующий
`shutdown()` и очередь F6–F7, не меняя журнал F3–F5. Проверяется отсутствие
неподтверждённого восстановления; незавершённый журнал не удаляется.

При ошибке окно остаётся открытым. Пользователь может повторить очистку,
отменить выход либо явно выйти несмотря на предупреждение. Принудительный
выход через этот диалог сохраняет незавершённый журнал для Crash Recovery.
Отмена снимает блокировку клиента, возвращает опрос и согласование прокси.
Если защита после отмены не подтверждена, клиент показывает предупреждение.

Системные службы systemd/SCM продолжают работу. Для console mode перед финальным
выходом проверяется текущая информация демона и выполняется один успешный
`disconnect` через существующий API. GUI не убивает внешние процессы по имени
или порту: он не владеет PID отдельно запущенного velumd, поэтому его API-процесс
может остаться запущенным после остановки сетевого ядра. Ошибка подтверждения
отключения также требует решения пользователя.

## Границы гарантий

SIGKILL, TerminateProcess, авария runtime, принудительное уничтожение окна или
аварийное завершение ОС могут оборвать процесс без асинхронной очистки.
Перехват штатного закрытия этих случаев не устраняет. Сохранённый журнал
используется Crash Recovery при следующем запуске; при чужих изменениях
сохраняются проверки конфликтов. ОС может ограничить время при logout/shutdown,
поэтому завершение пользовательского диалога и очистка тогда не гарантируются.

Проверки используют mock platform channels и менеджер настроек в памяти.
Linux release-сборка не является проверкой реальных GTK/WM событий на каждом DE.
Компиляция Windows runner в COFF-объект MinGW с заголовками текущего Flutter
проверяет C++ интерфейсы, но не линковку Windows приложения и не Windows runtime.

## Проверка F9

`test/tray_availability_test.dart` использует управляемые Future/Completer,
ручные одноразовые таймеры и адаптеры в памяти. Проверяет отсутствие/появление
панели, потерю host и регистрации, окно check/hide, конкурентные show/hide,
устаревшие ответы, ошибки D-Bus и native show, повторную регистрацию, dispose
при скрытом окне/незавершённой операции, повторную инициализацию, выход и отсутствие
проверок на telemetry ticks. Существующие тесты F8 остаются частью общей проверки.

Отдельный opt-in тест с настоящим GTK-окном, SNI и Waybar:

```sh
scripts/test-linux-tray.sh --isolated-session
```

Нужны рабочая Wayland-сессия Hyprland, hyprctl, Flutter Linux toolchain, Waybar, gdbus,
dbus-run-session, jq и timeout. Скрипт собирает `tool/tray_lifecycle_smoke.dart`,
запускает GUI и свою временную панель на отдельном D-Bus. На текущем дисплее
кратковременно появляется дополнительная панель; пользовательская панель не
останавливается. Завершаются только дочерние процессы, созданные этим тестом.
Демон/VPN-клиент не инициализируется, токены/профили не читаются, сетевые настройки
не меняются. Тест проверяет реальную видимость через Linux runner и mapped-окно
с собственным PID в Hyprland (метаданные остальных окон не сохраняются).
Сохраняет runtime.log/results.json в напечатанном `/tmp/velum-f9-smoke.*`.

Проверяемые native-сценарии: запуск без панели; позднее появление Waybar и скрытие;
автоматический показ после остановки тестового Waybar; его повторное появление и
новое скрытие; потеря SNI-регистрации при работающей панели; показ после dispose.
Для обычного bundle после этого теста выполнить `flutter build linux --release`
из app: smoke использует тот же каталог сборки, но копирует свой bundle в /tmp.

2026-11-16 все шесть native-сценариев прошли на Hyprland 0.56.2 с Waybar 0.15.0,
на настоящем Wayland-дисплее и отдельной тестовой D-Bus-сессии. Конкурентные
операции и ошибки проверены отдельно адаптерами в памяти. GNOME/KDE и
перезапуск самого session bus нельзя считать подтверждёнными этим сценарием.
SNI host/item подтверждает протокольную доступность, но не доказывает, что панель
визуально рисует значок или не зависла, сохранив регистрацию. Если GTK show
постоянно не работает, UI isolate не выполняется или процесс уничтожен, Dart-
наблюдение не гарантирует восстановление. SIGKILL/аварии остаются за его пределами.
