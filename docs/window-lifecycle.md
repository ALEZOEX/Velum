# Управляемое закрытие GUI (F8)

Канал `velum/window` обслуживает оба направления:

- GTK `delete-event` и Windows `WM_CLOSE` всегда блокируют обычное уничтожение
  окна и посылают Dart событие `closeRequested`.
- Flutter X вызывает `VelumTrayService.handleWindowClose()`. Пункт «Выход»
  вызывает `exitApplication()`, который игнорирует настройку сворачивания.
- Только команда Dart `closeConfirmed`, отправленная после очистки либо после
  явного согласия пользователя на небезопасный выход, разрешает окончательное
  закрытие. Нативный флаг разрешения предотвращает рекурсивный запрос.
- Если Dart ещё не готов, отсутствие обработчика не разрешает закрыть окно.

Контроллер выполняет один запрос закрытия за раз. Повторные X, Alt+F4 и «Выход»
присоединяются к этому Future. Начатые обновления трея дожидаются завершения,
а его уничтожение выполняется один раз. Прямого `exit(0)` больше нет.

## Скрытие

При включённом minimizeToTray скрытие допускается после создания иконки и
проверки её доступности непосредственно перед действием. Linux дополнительно
проверяет зарегистрированный SNI host и наличие элемента текущего процесса в
`RegisteredStatusNotifierItems`; одной доступности session D-Bus недостаточно.
Если `gdbus` отсутствует, запрос не подтверждён либо формат регистрации не
распознан, окно не скрывается. Windows использует фактическую видимость иконки
из nativeapi, которая проверяет её наличие в Shell.

Это проверка перед закрытием, а не полное исправление F9: постоянное наблюдение
за исчезновением панели и повторная регистрация иконки сюда не входят. Между
проверкой и скрытием host всё ещё может исчезнуть.

## Завершение и ошибки

При возможном активном соединении GUI сначала предупреждает об изменении
защиты/пути трафика. После согласия `prepareForExit()` использует существующий
`shutdown()` и очередь F6–F7, не меняя журнал F3–F5. Проверяется отсутствие
неподтверждённого восстановления; незавершённый журнал не удаляется.

При ошибке окно остаётся открытым. Пользователь может повторить очистку,
отменить выход либо явно выйти несмотря на предупреждение. Принудительный
выход через этот диалог сохраняет незавершённый журнал для Crash Recovery.
Отмена снимает блокировку клиента, возвращает опрос и согласование прокси.
Если защита после отмены не подтверждена, клиент показывает предупреждение.

Системные службы systemd/SCM продолжают работу. Для console mode перед финальным
выходом проверяется текущая информация демона и выполняется один успешный
`disconnect` через существующий API. GUI не убивает внешние процессы по имени
или порту: он не владеет PID отдельно запущенного velumd, поэтому его API-процесс
может остаться запущенным после остановки сетевого ядра. Ошибка подтверждения
отключения также требует решения пользователя.

## Границы гарантий

SIGKILL, TerminateProcess, авария runtime, принудительное уничтожение окна или
аварийное завершение ОС могут оборвать процесс без асинхронной очистки.
Перехват штатного закрытия этих случаев не устраняет. Сохранённый журнал
используется Crash Recovery при следующем запуске; при чужих изменениях
сохраняются проверки конфликтов. ОС может ограничить время при logout/shutdown,
поэтому завершение пользовательского диалога и очистка тогда не гарантируются.

Проверки используют mock platform channels и менеджер настроек в памяти.
Linux release-сборка не является проверкой реальных GTK/WM событий на каждом DE.
Компиляция Windows runner в COFF-объект MinGW с заголовками текущего Flutter
проверяет C++ интерфейсы, но не линковку Windows приложения и не Windows runtime.
