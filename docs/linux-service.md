# Системный TUN на Linux

Локальный SOCKS/HTTP-прокси сам по себе не перенаправляет трафик приложений. Для системной маршрутизации Velum использует TUN и отдельную привилегированную службу; Flutter-интерфейс запускается обычным пользователем.

## Установка

Из корня проверенной копии репозитория сначала соберите бинарники и подготовьте токен **от обычного пользователя**:

```bash
python3 scripts/init-client.py
make core daemon
```

Если для XHTTP используется Xray companion, сначала соберите или загрузите проверенный `bin/xray`. Установщик включит его только при наличии этого файла. Версии и способы проверки ядра определены сборкой проекта; установщик сам не скачивает исполняемые файлы.

Прочитайте `scripts/install-linux-service.sh`, затем выполните:

```bash
sudo ./scripts/install-linux-service.sh
```

Установка запросит системный пароль. При прямом запуске от root или из другого контекста явно укажите владельца GUI:

```bash
sudo ./scripts/install-linux-service.sh --user alezoex
```

Пользователь определяется из `SUDO_USER` либо `PKEXEC_UID`; домашний каталог — из базы пользователей ОС. Установщик не использует `$HOME` процесса root для поиска токена. Для нестандартного каталога конфигурации доступен `--config-dir /полный/путь`; GUI должен использовать тот же каталог через `VELUM_CONFIG_DIR`.

После установки откройте сетевые настройки Velum, выберите **TUN** и подключите профиль. Установка и запуск службы разрешают создание TUN, но сами не подключают VPN и не изменяют выбранный профиль. Служба автоматически запускается при загрузке ОС, а пользовательское подключение по-прежнему управляется GUI.

Если одновременно используется Happ или другой VPN, сначала отключите его туннель перед проверкой системной маршрутизации Velum. Установщик не отключает сторонние VPN. При необходимости можно явно выбрать физический исходящий интерфейс:

```bash
sudo ./scripts/install-linux-service.sh --interface wlan0
```

Имя интерфейса зависит от машины. При явной привязке переход Wi-Fi/Ethernet не происходит автоматически; без параметра используется автоматическое определение интерфейса ядром.

## Конфликт с ранее запущенной proxy-службой

Интерфейс API занимает `127.0.0.1:27841`. Если этот порт занят вручную запущенным `velumd`, установщик откажется запускать новую службу. Остановите старый процесс в том терминале, где он запущен, и повторите команду. Установщик не завершает процессы по имени или номеру порта.

Для установки файлов без запуска:

```bash
sudo ./scripts/install-linux-service.sh --no-start
sudo systemctl enable --now velum.service
```

## Что устанавливается

- `/usr/local/lib/velum/velumd`, `sing-box` и при наличии `xray`: владелец root, режим 0755; каталог недоступен на запись обычному пользователю.
- `/etc/velum/token`: приватная root-копия существующего GUI-токена, режим 0600; значение не выводится. Каталог имеет режим 0700.
- `/etc/systemd/system/velum.service`: системная служба с `--tun`, политикой `KillMode=control-group`, ограниченными сетевыми capabilities и отдельным каталогом `/run/velum`.

Профили и настройки пользователя не копируются в системные каталоги и не меняются. Привилегированный процесс получает выбранный профиль через авторизованный локальный API. Один экземпляр службы рассчитан на одного владельца GUI-токена. При смене токена или владельца повторите установку.

Обновление устанавливает подготовленные бинарники и сохраняет резервную копию предыдущих файлов до успешного старта. Если запуск или авторизованная проверка API не проходят, установщик восстанавливает предыдущие файлы и состояние systemd. Проверка API подтверждает готовность службы и разрешение TUN; она не доказывает доступность конкретного VPN-сервера или отсутствие утечек в вашей сети.

## Диагностика и удаление

```bash
systemctl status velum.service
sudo journalctl -u velum.service -n 80 --no-pager
sudo systemctl stop velum.service
sudo ./scripts/uninstall-linux-service.sh
```

Удаление останавливает службу и дочерние ядра, убирает unit, системные бинарники и системную копию токена. Пользовательские профили, настройки и исходный токен сохраняются. Остановка systemd дожидается штатной очистки TUN ядром; аварийные случаи SIGKILL или отключения питания требуют отдельных проверок восстановления сети. Kill switch этим установщиком не добавляется.

Настройки жизненного цикла и ограничений сверены с официальной документацией [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) и [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html). Реальная установка требует системной авторизации и должна проверяться отдельно от проверки синтаксиса скриптов.

## F15: layout, повторная установка и граница доверия

Установщик использует два явных расположения, независимо от рабочего каталога:

| Файл | Репозиторий / распакованный исходный bundle | Установленная служба |
| --- | --- | --- |
| Установщик | `scripts/install-linux-service.sh` | `/usr/local/lib/velum/install-service.sh` |
| Общий модуль | `scripts/linux_service_installer.py` | `/usr/local/lib/velum/linux_service_installer.py` |
| Удаление | `scripts/uninstall-linux-service.sh` | `/usr/local/lib/velum/uninstall-service.sh` |
| Управление | `packaging/linux/velum-service-control` | `/usr/local/lib/velum/velum-service-control` |
| Polkit policy | `packaging/linux/app.velum.service.policy` | `/usr/local/lib/velum/app.velum.service.policy` и `/usr/share/polkit-1/actions/app.velum.service.policy` |
| Бинарники | `bin/velumd`, `bin/sing-box`, необязательный `bin/xray` | В том же каталоге, что установленный установщик |

Ни один обязательный файл управления не считается необязательной частью упаковки.
Нельзя раздавать только `install-service.sh`: ему нужен Python-модуль рядом.
Исходный bundle должен сохранять дерево `scripts/`, `packaging/linux/`, `bin/`.
Установленная копия сама содержит полный набор для повторной установки;
поиск `/usr/local/lib/bin` больше не используется. Python 3, Bash, GNU stat,
systemd и Polkit — системные зависимости, не встраиваемые в bundle.

GUI вызывает абсолютный `/usr/bin/pkexec` с установленным
`/usr/local/lib/velum/velum-service-control install --token-file <фактический путь>`.
Это тот же helper, который указан в Polkit policy. Владелец GUI определяется
через числовой `PKEXEC_UID`, а не `$USER` или `$HOME` root-процесса.
`VELUM_CONFIG_DIR` и `VELUM_TOKEN_FILE` учитываются GUI: установщик получает
уже выбранный абсолютный путь токена. Сам токен не передаётся в аргументах.
Команды systemd вызываются через `/usr/bin/systemctl` с фиксированным окружением;
Python запускается с `-I`, без пользовательских import paths.

Первоначальная доверенная установка по-прежнему требует явной авторизации:
запуск проверенного скрипта из репозитория администратором либо установка
bundle в доверенное root-owned дерево. GUI не повышает права скрипту из
пользовательского каталога. Для root-owned checkout GUI может найти установщик
по родителям пути своего исполняемого файла, без зависимости от cwd.
Старая установленная версия **не содержит нового Python-модуля**: её нужно один
раз обновить проверенным установщиком из репозитория. Это миграция установщика,
а не ручное указание `--bin-dir`. После неё обычная переустановка из GUI не
требует пути к бинарникам. Переустановка использует текущие установленные
бинарники, обновление новой версией выполняется из нового проверенного bundle.

Перед Polkit GUI проверяет root-владельца, тип, отсутствие ссылок/hardlinks,
прав записи другим пользователям для entry point, Python-модуля и родителей.
Привилегированный модуль проверяет независимо все компоненты путей и каждый
используемый файл: `O_NOFOLLOW`, тип объекта, владельца, режим, число hardlinks
и POSIX ACL. Расширенные/default ACL отклоняются для ручной проверки, а не
«исправляются» автоматически. В исходной копии допустимы root и выбранный
GUI-пользователь; sticky root-owned предки вроде `/tmp` допустимы только при
чтении исходных файлов. В установленном дереве допустим только root, без записи
группе/остальным. Входные файлы читаются через открытые дескрипторы до публикации;
проверяется изменение размера/mtime/ctime во время чтения. Это не подпись
бинарника: администратор должен доверять исходному bundle и GUI-пользователю,
чьи бинарники он явно разрешил установить.

Публикация файлов использует новые временные файлы с `O_EXCL`, `fsync` и rename
относительно удерживаемых дескрипторов root-каталогов. Существующий файл никогда
не открывается с усечением. Записывается root-owned `manifest.json` с точным
списком и SHA-256 содержимого установленного дерева. Manifest подтверждает
принадлежность файлов этой установке; он не заменяет проверку происхождения.
Если systemd уже загрузил `velum.service` из другого unit (например, vendor-файла),
установщик отказывается останавливать, заменять или удалять такую службу.
Неизвестный файл, вложенный каталог, symlink, hardlink, другой владелец,
небезопасный режим либо несовпадение manifest вызывают отказ **до остановки**
службы. Нет автоматического удаления, смены владельца или расширения списка.
Старое дерево без manifest принимается только при точном совпадении генерируемого
unit, безопасных известных файлах и совпадении policy; после обновления получает
manifest. Существующий Xray не удаляется молча, если новый bundle его не содержит.
Настройка исходящего интерфейса сохраняется при переустановке, если новый
`--interface` явно не передан.

Откат при обычном исключении или первом SIGTERM возвращает бинарники, unit,
policy, системный токен и прежнее enabled/active состояние. Для ранее работавшей
службы после отката проверяется авторизованный API. Перед явным запуском
опубликованной или возвращённой службы сбрасывается failed/start-limit состояние
только `velum.service`: серия падений новой версии не должна заблокировать запуск
старой. StartLimit и `Restart=on-failure` не отключаются. Перед заменой файлов
установщик останавливает собственный unit также в неактивном/activating состоянии,
чтобы отложенный systemd restart не запустил частично опубликованную версию. Частичная запись staging
не останавливает старую службу. Удаление также сначала сохраняет бинарники
переименованием и может вернуть прежнюю службу при отказе daemon-reload.
Удаляются только заранее проверенные имена: рекурсивного `rm -rf` в production
нет. Неизвестные дополнительные файлы в `/etc/velum` сохраняются.

Перед изменением службы исходные unit, policy и токен сохраняются также на диске:
`/etc/.velum-recovery-*`, root:0700, файлы 0600; `state.json` содержит исходные
режимы и состояние службы, без значения токена. Успешная транзакция или полный
откат удаляют эти приватные копии.

Если сам откат невозможен (например, повторно отказывает systemd или файловая
система), возвращается явная ошибка `ROLLBACK INCOMPLETE` с путями для проверки;
приватные оригиналы на диске и сохранившиеся бинарные резервные копии не уничтожаются. Их нельзя автоматически удалять
ради повторной установки. SIGKILL, падение питания и сбой диска не дают гарантии
полного отката: межкаталожная транзакция не является crash-atomic, постоянного
журнала автоматического возобновления пока нет. Согласованное изменение файлов
другим root-процессом также выходит за модель защиты. Временные резервные
каталоги при такой аварии требуют отдельной ручной проверки администратора.

## Безопасная проверка установщика

```bash
# Без sudo: отдельные user/mount/PID/network namespaces и временная файловая система.
# Нужны util-linux (unshare/mount), chroot, iproute2, Python 3, настроенные subordinate UID/GID.
./scripts/test-linux-service-installer.sh
```

Набор проверяет реальную запись/rename/удаление в приватном дереве, два layout,
обновление, повторную установку, токен, Xray, права, ACL, ссылки, чужие файлы,
ошибки staging/публикации/запуска/удаления и откат. Вместо systemd используется
тестовый адаптер и инертный авторизованный HTTP API в изолированной сети.
`/dev/net/tun` в этом окружении — фикстура `/dev/null`: TUN не создаётся.
Отказ изоляции завершает тест; fallback на sudo или основную систему отсутствует.

Отдельный CI job `Linux service installer / disposable VM` выполняет настоящие
install/start/stop/upgrade/reinstall/uninstall через systemd в одноразовой
GitHub-hosted Ubuntu VM с реальным `velumd`. Ядра — инертные version-only
фикстуры, отказывающие любым командам подключения. Запросы connect не отправляются.
Состояние IPv4/IPv6 маршрутов и policy rules сверяется до/после. Скрипт VM-проверки
отказывается работать вне явно выбранной GitHub-hosted VM; его нельзя запускать
на основной машине. JSON-отчёт сохраняется как CI artifact. Некоторые каталоги GitHub runner могут
быть доступны на запись runner-пользователю: VM-тест сначала проверяет отказ
установщика для исходных прав, затем **сам тест** явно подготавливает доверенных
root-предков без расширенных/default POSIX ACL и возвращает исходных владельцев,
режимы и ACL после удаления службы. ACL удаляются только подготовкой одноразовой
VM и её временного input bundle, а не production-установщиком. Production-установщик
никогда не меняет владельцев и права небезопасных существующих каталогов ради
продолжения установки. Подготовка VM не подтверждает работу в недоверенном дереве.

Эти проверки не заменяют ручной end-to-end тест Polkit Authentication Agent и
GUI на физическом Linux. Для него используйте отдельную VM: установите проверенный
bundle, откройте GUI обычным пользователем с приватным токеном, подтвердите
установку/повторную установку, затем проверьте `systemctl status`, владельцев и
режимы файлов, совпадение токенов без вывода значений и удаление. VPN/TUN
подключать для проверки установщика не требуется. Поведение конкретных Polkit
агентов и GUI-диалогов остаётся непроверенным до такого испытания.
