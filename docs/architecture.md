# Архитектура MVP

Flutter хранит профили и настройки, импортирует подписки непривилегированно. Go-служба получает URI профиля и проверяемые настройки маршрутизации, генерирует JSON, проверяет его sing-box и управляет единственным процессом ядра. Никаких команд shell, загруженных скриптов или произвольного JSON ядра в IPC нет.

MVP использует HTTP/1.1 на фиксированном IPv4 loopback `127.0.0.1:27841` с Bearer-токеном 256 бит. CORS не включён. Токен сравнивается за постоянное время. Все запросы требуют токен, включая статус. Ограничены тело запроса, заголовки и таймауты. Это осознанное упрощение относительно UDS/Named Pipe; переход к этим транспортам позволит опираться на идентичность пользователя ОС.

API v1: авторизованные запросы статуса, подключения и отключения, повторного подключения, проверки соединения, TCP-пробы и чтения/очистки журнала. Конкретные поля описаны типами в `daemon/main.go` и `daemon/settings.go`. Статистика получается через локальный Clash API с отдельным случайным секретом.

Состояния: `disconnected`, `running`, `error`; GUI добавляет `offline` при недоступной службе. `running` не означает проверенное подключение к серверу. Подключение нового профиля останавливает старое. Ошибки валидации возвращают HTTP 400; неверный токен — 401. API не возвращает секретную ссылку.

Операции сериализованы mutex. После запуска отдельная goroutine ожидает процесс, не захватывая mutex. При остановке: Interrupt, ожидание до 4 секунд, затем Kill и обязательный Wait. SIGINT/SIGTERM завершают службу и дочернее ядро. SIGKILL/авария самой службы пока могут оставить дочерний процесс: системный supervisor с kill-control-group — следующий шаг.

Конфиг с секретами создаётся в отдельном временном каталоге 0700, файл 0600, удаляется при штатном завершении. Ограниченный журнал ядра передаётся GUI после удаления известных секретов; не следует считать произвольные диагностические данные гарантированно обезличенными. Профили сохраняются атомарным rename внутри приватного каталога пользователя.

Ядро закреплено на 1.12.12 и собирается Go toolchain с `with_utls,with_quic,with_clash_api`; сборка исходников проходит через Go module verification. Обновление ядра требует повторения конфигурационных и сетевых тестов. Не переносить поля из документации testing в закреплённую версию без проверки.

DNS: endpoint разрешается системным резолвером перед TUN; в конфиге используется IP, исходное имя остаётся SNI. DoH 1.1.1.1 доступен через outbound proxy, DNS из TUN перехватывается правилом hijack-dns. Прямые доменные/CIDR-исключения добавляются после DNS/sniff правил. Реальное отсутствие DNS/IPv6-утечек должно проверяться packet capture на каждой ОС; один валидный JSON этого не доказывает.

## Следующие этапы

1. Linux: systemd-установка, IPC UDS с авторизацией пользователя, восстановление после аварии, сетевые тесты TUN/IPv6/DNS/смены сети.
2. Отдельный kill switch с управлением firewall и явной политикой fail-open/fail-closed; его нельзя эмулировать состоянием кнопки.
3. Windows: Service host, Named Pipe ACL, Wintun, установщик и проверка удаления/обновления.
4. Расширить сетевые тесты health check, статистики и сценариев восстановления при смене сети.
5. Android VpnService с защитой сокетов и отдельным lifecycle; Flutter UI и модель профилей переиспользуются.

Нельзя загружать исполняемые файлы по адресу из подписки или позволять GUI выбирать бинарник/путь файла для привилегированной службы. Параметр CLI `--core` является ответственностью администратора при запуске и отсутствует в сетевом API.

## Явный исходящий интерфейс Linux

CLI --interface задаёт проверяемое при запуске имя существующего интерфейса. Компилятор конфигурации выключает route.auto_detect_interface и задаёт route.default_interface. Это позволяет тестировать proxy-соединение параллельно Happ, не направляя исходящий Reality-трафик в happ-xray. Значение не принимается по сетевому API. Без флага сохраняется автоматический выбор. Автоматическое переключение Wi-Fi/Ethernet при заданном флаге не реализовано.
